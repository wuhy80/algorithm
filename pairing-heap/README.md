# 配对堆 Pairing Heap

> 通过 meld 和两遍配对合并实现简洁的可并堆

## 先抓住一句话

**配对堆 Pairing Heap** 属于可并优先队列。核心操作 `meld` 只比较两个根，并把较大根连接为较小根的孩子。

学习时只盯住两件事：**当前状态表示什么**，以及**这一步为什么可以排除其他可能**。演示中的颜色、指针、队列、区间或节点变化，都是这两个问题的可视化表达。

## 为什么需要它

二叉堆合并两个队列并不高效。配对堆用多叉树和极简 meld 支持常数时间合并，并在删除最小值时集中整理根的孩子。

删除根后的两遍合并先把孩子两两配对，再从右向左累积合并，避免形成过于偏斜的结构。

## 心智模型

整棵堆只承诺父键不大于孩子键；每棵子堆的根都是其局部最小值，meld 后较小根自然成为整体最小值。

面对新题时，不要先问“该套哪个模板”，先问：

1. 输入中有什么结构可以利用，例如有序性、连续区间、树形依赖、图的边或重复子问题？
2. 当前保存的状态是否足以决定下一步？
3. 哪些候选已经可以被严格证明不可能，因而永远不用再看？

## 核心不变量

> 每条父子边满足堆序；meld 保留两棵输入堆的全部节点且只增加一条父子关系，返回根是两根中的较小者。

所谓不变量，就是算法每一步开始和结束时都必须为真的事实。调试 **配对堆 Pairing Heap** 时，最有效的方法不是盯着最终答案，而是在每次单步后检查这条不变量。只要某一帧不再满足它，错误通常就在上一帧的边界更新、状态转移或数据结构维护中。

## 算法步骤

1. 插入时把单节点堆与当前根 meld。
2. 合并两堆时比较根，把较大根挂到较小根的孩子表。
3. 删除最小值时移除根，按从左到右把孩子两两 meld。
4. 再从右到左 meld 第一遍结果，得到新根。

演示把这些步骤保存为一系列状态快照。先单步执行，确认自己能预测下一帧，再使用连续播放。若只看动画而不预测，容易记住颜色变化，却没有真正掌握决策依据。

## 框架伪代码

下面的伪代码刻意忽略页面绘制和工程细节，只保留这类算法最值得迁移的骨架：

```text
meld(a, b):
    if one is null: return the other
    if b.key < a.key: swap(a, b)
    make b a child of a
    return a

delete_min(root):
    pairs = meld adjacent children from left to right
    return meld pairs from right to left
```

把伪代码映射到本目录的 `app.js` 时，可以按“解析输入 → 初始化状态 → 生成每一步 → 更新指标 → Canvas 绘制”的顺序阅读。算法逻辑负责决定状态，绘图逻辑只负责把状态呈现出来，两者不要混在一起理解。

## 复杂度怎么分析

**结论：meld O(1)，delete-min 摊还 O(log n)**

不要只背大 O。分析时分三步：先数一共有多少个状态或元素，再数每个状态被处理多少次，最后把排序、堆操作、哈希查询、递归深度或额外表格单独计入。若算法具有摊还或期望复杂度，还要说明“总成本如何分摊”或“随机性假设是什么”。

## 常见错误

- meld 后没有正确断开或重接兄弟指针，造成节点丢失或环。
- 删除最小值时只做第一遍配对，没有从右向左汇总。
- decrease-key 后没有把降键节点从原父节点正确剪下再与根合并。
- 只用默认样例验证，没有测试空结构、单元素、重复值、断开输入或最大边界。
- 把演示中的视觉位置当作算法状态；真正应该验证的是数据、索引、距离、计数或引用关系。

## 什么时候使用

适合：需要频繁 meld、插入和删除最小值，并希望实现比复杂可并堆更简单的优先队列。

不适合：要求简单数组布局、严格最坏界或快速任意键查找的场景。
