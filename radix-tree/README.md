# Patricia / Radix Tree

> 把 Trie 的单孩子路径压缩为字符串边以减少节点

## 先抓住一句话

**Patricia / Radix Tree** 属于压缩前缀索引。它把 Trie 中连续单孩子路径合并为字符串边，减少节点和指针数量。

学习时只盯住两件事：**当前状态表示什么**，以及**这一步为什么可以排除其他可能**。演示中的颜色、指针、队列、区间或节点变化，都是这两个问题的可视化表达。

## 为什么需要它

普通 Trie 对长公共路径仍会为每个字符分配节点。Radix Tree 把不发生分叉的路径压缩成一条边，同时保留前缀分支语义。

插入的关键是计算剩余键与边标签的最长公共前缀，并在公共前缀结束处拆边。

## 心智模型

一条边可以消费多个字符；查询每走一步，都要完整匹配当前边标签后才能进入孩子。

面对新题时，不要先问“该套哪个模板”，先问：

1. 输入中有什么结构可以利用，例如有序性、连续区间、树形依赖、图的边或重复子问题？
2. 当前保存的状态是否足以决定下一步？
3. 哪些候选已经可以被严格证明不可能，因而永远不用再看？

## 核心不变量

> 根到节点的边标签拼接等于该节点前缀；同一节点的孩子边首字符互不相同，内部非终点节点不保留可继续压缩的单孩子链。

所谓不变量，就是算法每一步开始和结束时都必须为真的事实。调试 **Patricia / Radix Tree** 时，最有效的方法不是盯着最终答案，而是在每次单步后检查这条不变量。只要某一帧不再满足它，错误通常就在上一帧的边界更新、状态转移或数据结构维护中。

## 算法步骤

1. 在当前节点按首字符选择候选边。
2. 比较边标签与剩余键的最长公共前缀。
3. 完全匹配边时继续下降；部分匹配时创建中间节点并拆分旧边。
4. 插入结束处设置终点标记，删除后合并可压缩的单孩子节点。

演示把这些步骤保存为一系列状态快照。先单步执行，确认自己能预测下一帧，再使用连续播放。若只看动画而不预测，容易记住颜色变化，却没有真正掌握决策依据。

## 框架伪代码

下面的伪代码刻意忽略页面绘制和工程细节，只保留这类算法最值得迁移的骨架：

```text
insert(node, suffix):
    edge = child edge sharing suffix[0]
    if no edge: add edge labeled suffix to terminal leaf
    else:
        p = longest_common_prefix(edge.label, suffix)
        if p == edge.label: insert(edge.child, suffix after p)
        else: split edge at p and attach old/new remainders
```

把伪代码映射到本目录的 `app.js` 时，可以按“解析输入 → 初始化状态 → 生成每一步 → 更新指标 → Canvas 绘制”的顺序阅读。算法逻辑负责决定状态，绘图逻辑只负责把状态呈现出来，两者不要混在一起理解。

## 复杂度怎么分析

**结论：插入和查询 O(key length)**

不要只背大 O。分析时分三步：先数一共有多少个状态或元素，再数每个状态被处理多少次，最后把排序、堆操作、哈希查询、递归深度或额外表格单独计入。若算法具有摊还或期望复杂度，还要说明“总成本如何分摊”或“随机性假设是什么”。

## 常见错误

- 部分匹配时覆盖旧边，丢失原有键的剩余后缀。
- 查询只比较边标签首字符，没有验证整段标签。
- 删除后盲目合并节点，忽略当前节点本身可能是完整键终点。
- 只用默认样例验证，没有测试空结构、单元素、重复值、断开输入或最大边界。
- 把演示中的视觉位置当作算法状态；真正应该验证的是数据、索引、距离、计数或引用关系。

## 什么时候使用

适合：字符串或位前缀键很多、普通 Trie 单孩子链较长，并且需要前缀检索的场景。

不适合：只需要完整键等值查询，或键很短且压缩带来的字符串比较成本得不偿失。
