# Kosaraju 强连通分量

> 按完成序在原图和转置图执行两遍 DFS

## 先抓住一句话

**Kosaraju 强连通分量** 用两轮 DFS 分解有向图：第一轮确定分量在缩点 DAG 上的完成先后，第二轮在转置图上按完成时间逆序一次取出一个完整强连通分量。

学习时只盯住两件事：**当前状态表示什么**，以及**这一步为什么可以排除其他可能**。演示中的颜色、指针、队列、区间或节点变化，都是这两个问题的可视化表达。

## 为什么需要它

只从某个顶点做可达搜索，无法判断“互相可达”，也无法可靠划分所有分量。Kosaraju 用第一轮 DFS 的完成序找出尚未处理部分中的缩点源，再借助转置图把该源分量的入边翻转为出边边界，从而完整收集这个分量。

## 心智模型

把每个强连通分量缩成一个点后，图一定是 DAG。第一轮 DFS 最晚完成的未处理分量位于这个 DAG 的源端；反转所有边后，从它出发只能访问本分量，不能越过边界进入尚未处理的其他分量。

面对新题时，不要先问“该套哪个模板”，先问：

1. 输入中有什么结构可以利用，例如有序性、连续区间、树形依赖、图的边或重复子问题？
2. 当前保存的状态是否足以决定下一步？
3. 哪些候选已经可以被严格证明不可能，因而永远不用再看？

## 核心不变量

> 第一轮中，节点只在全部后继处理完成后进入完成序列。第二轮每次取完成时间最大的未分配节点，并在转置图上搜索，访问到的节点恰好构成一个完整 SCC，且不会混入其他未分配分量。

所谓不变量，就是算法每一步开始和结束时都必须为真的事实。调试 **Kosaraju 强连通分量** 时，最有效的方法不是盯着最终答案，而是在每次单步后检查这条不变量。只要某一帧不再满足它，错误通常就在上一帧的边界更新、状态转移或数据结构维护中。

## 算法步骤

1. 建立原图 `graph` 和每条边反向后的转置图 `reverse_graph`。
2. 在原图上从所有未访问顶点启动 DFS，退出节点时把它追加到完成序列。
3. 清空访问标记，按完成序列的逆序检查顶点。
4. 每遇到一个尚未分配的顶点，就在转置图上启动 DFS；本次访问到的全部顶点使用同一个 SCC 编号。

演示把这些步骤保存为一系列状态快照。先单步执行，确认自己能预测下一帧，再使用连续播放。若只看动画而不预测，容易记住颜色变化，却没有真正掌握决策依据。

## 框架伪代码

下面的伪代码刻意忽略页面绘制和工程细节，只保留这类算法最值得迁移的骨架：

```text
dfs_order(u):
    visited[u] = true
    for v in graph[u]:
        if not visited[v]: dfs_order(v)
    order.push(u)

dfs_component(u, id):
    component[u] = id
    for v in reverse_graph[u]:
        if component[v] is unset: dfs_component(v, id)

run dfs_order from every unvisited vertex
for u in reverse(order):
    if component[u] is unset: dfs_component(u, new_id)
```

把伪代码映射到本目录的 `app.js` 时，可以按“解析输入 → 初始化状态 → 生成每一步 → 更新指标 → Canvas 绘制”的顺序阅读。算法逻辑负责决定状态，绘图逻辑只负责把状态呈现出来，两者不要混在一起理解。

## 复杂度怎么分析

**结论：O(V + E)，额外空间复杂度为 O(V+E)。**

不要只背大 O。分析时分三步：先数一共有多少个状态或元素，再数每个状态被处理多少次，最后把排序、堆操作、哈希查询、递归深度或额外表格单独计入。若算法具有摊还或期望复杂度，还要说明“总成本如何分摊”或“随机性假设是什么”。

## 常见错误

- 节点在进入 DFS 时就加入序列，得到发现序而不是完成序。
- 第二轮仍在原图上搜索，或没有把每一条边正确加入转置图。
- 第二轮按完成时间正序处理，导致一次搜索跨越多个 SCC。
- 第一轮只从一个固定起点开始，遗漏不可达顶点和孤立点。
- 只用默认样例验证，没有测试空结构、单元素、重复值、断开输入或最大边界。
- 把演示中的视觉位置当作算法状态；真正应该验证的是数据、索引、距离、计数或引用关系。

## 什么时候使用

适合：静态有向图的 SCC 分解、缩点建 DAG，以及希望用两次结构清晰的 DFS 理解强连通性的场景。

不适合：内存不足以同时保存原图和转置图，或图持续动态变化、每次更新后都要在线维护 SCC 的场景。

## 自测问题

- 为什么第一轮必须记录完成序，而不能使用发现序？
- 为什么第二轮要反转边，并按完成时间从大到小启动搜索？
- 把演示输入缩小到 3 到 6 个元素，能否在纸上预测下一帧再点击“单步”？
- 当前复杂度的主导项来自哪里？换一种底层数据结构后会怎样变化？

## 实现判定细节

- 第一遍 DFS 记录的是完成时间顺序，节点必须在所有后继处理完后入栈；发现顺序不能替代完成顺序。
- 第二遍在转置图上按完成时间逆序启动 DFS，每次新启动得到一个完整强连通分量。
- 原图和转置图必须包含完全相同的节点集合，孤立点也要参与两遍扫描。
- 分量缩点后一定得到 DAG；可用这一性质反向检查分量编号和跨分量边是否合理。
