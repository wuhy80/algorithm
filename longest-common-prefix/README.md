# 最长公共前缀 Longest Common Prefix

> 逐列比较一组单词并停止在第一个不一致字符

## 先抓住一句话

**最长公共前缀 Longest Common Prefix** 从索引 0 开始逐列比较多个字符串；第一列不一致的位置就是公共前缀的右边界。

学习时只盯住两件事：**当前状态表示什么**，以及**这一步为什么可以排除其他可能**。演示中的颜色、指针、队列、区间或节点变化，都是这两个问题的可视化表达。

## 为什么需要它

公共前缀必须从每个字符串的起点开始，因此不需要枚举匹配起点或构造跳转表。只需扫描到最短字符串末尾或首个不一致字符。

一旦第 i 列出现差异，任何更长前缀都会包含这处差异，可以立即停止。

## 心智模型

把字符串竖直对齐成多行。逐列确认这一列是否全部相同，已经通过的连续列就是当前答案。

面对新题时，不要先问“该套哪个模板”，先问：

1. 输入中有什么结构可以利用，例如有序性、连续区间、树形依赖、图的边或重复子问题？
2. 当前保存的状态是否足以决定下一步？
3. 哪些候选已经可以被严格证明不可能，因而永远不用再看？

## 核心不变量

> 检查第 i 列前，所有字符串的前 i 个字符都相同；若第 i 列不全相同，则最长公共前缀长度恰好为 i。

所谓不变量，就是算法每一步开始和结束时都必须为真的事实。调试 **最长公共前缀 Longest Common Prefix** 时，最有效的方法不是盯着最终答案，而是在每次单步后检查这条不变量。只要某一帧不再满足它，错误通常就在上一帧的边界更新、状态转移或数据结构维护中。

## 算法步骤

1. 空字符串列表按接口约定返回空前缀。
2. 找到最短字符串，其长度给出扫描上界。
3. 对每个列索引 i，把其余字符串的字符与基准字符串第 i 个字符比较。
4. 首次不一致时返回基准字符串的前 i 个字符；全部一致则返回最短字符串。

演示把这些步骤保存为一系列状态快照。先单步执行，确认自己能预测下一帧，再使用连续播放。若只看动画而不预测，容易记住颜色变化，却没有真正掌握决策依据。

## 框架伪代码

下面的伪代码刻意忽略页面绘制和工程细节，只保留这类算法最值得迁移的骨架：

```text
longest_common_prefix(words):
    if words is empty: return ""
    limit = minimum length among words
    for i in 0 .. limit - 1:
        expected = words[0][i]
        if any word[i] != expected:
            return words[0][0:i]
    return words[0][0:limit]
```

把伪代码映射到本目录的 `app.js` 时，可以按“解析输入 → 初始化状态 → 生成每一步 → 更新指标 → Canvas 绘制”的顺序阅读。算法逻辑负责决定状态，绘图逻辑只负责把状态呈现出来，两者不要混在一起理解。

## 复杂度怎么分析

**结论：时间 O(S)，S 为全部检查字符数，空间 O(1)**

不要只背大 O。分析时分三步：先数一共有多少个状态或元素，再数每个状态被处理多少次，最后把排序、堆操作、哈希查询、递归深度或额外表格单独计入。若算法具有摊还或期望复杂度，还要说明“总成本如何分摊”或“随机性假设是什么”。

## 常见错误

- 没有处理空列表或空字符串，直接访问第一个字符。
- 扫描上界使用最长字符串长度，导致较短字符串越界。
- 把公共前缀与公共子串或公共子序列混为一谈。
- 只用默认样例验证，没有测试空结构、单元素、重复值、断开输入或最大边界。
- 把演示中的视觉位置当作算法状态；真正应该验证的是数据、索引、距离、计数或引用关系。

## 什么时候使用

适合：路径、域名、词典分组和批量字符串的共同起始片段提取。

不适合：寻找任意位置的公共片段或允许跳过字符的公共序列；应分别考虑子串索引或 LCS。
